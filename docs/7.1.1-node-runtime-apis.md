# 7.1.1. Node.js Runtime APIs (`valyrian.js/node`)

`valyrian.js/node` is the Node.js API surface that lets the same Valyrian application render HTML outside the browser.

It prepares the Node.js environment that SSR and request-scoped execution need, then exposes the rendering, DOM and storage APIs that keep browser and Node.js execution aligned for the same application.

## One `current` API, Efficient in Each Runtime

Application code keeps the same public API and types in both environments. Continue to use `current.vnode`, `current.component` and `current.event` where the rendering or event flow provides them.

Internally, the renderer's base state is named `rendererState`. Node.js exposes `current` through a Proxy that resolves the renderer state associated with the active request. Concurrent SSR and test scopes therefore read and update their own current vnode, component and event instead of sharing that execution state.

The browser takes the direct path: `current` points to `rendererState.current`. Each browser access avoids Proxy traps and contextual state lookup because a browser render does not need Node.js request isolation.

This runtime-specific implementation keeps the isomorphic contract efficient. You can adopt `valyrian.js/node` for SSR and browser-oriented tests while the browser build retains direct access to its renderer state. The benefit is architectural rather than benchmarked: Valyrian.js pays for contextual resolution where concurrent request isolation requires it and removes that unnecessary indirection from the browser path.

The runtime split was verified through the direct browser branch, concurrent Node.js isolation, 508 passing tests with 1 skipped test, type checking and a successful build.

## Node.js Setup Side Effects

Importing `valyrian.js/node` makes these globals available for server-side rendering:

* `global.document` (lightweight DOM adapter)
* `global.FormData`
* `global.sessionStorage` and `global.localStorage` backed by `ServerStorage`
* `global.Event`, `global.MouseEvent`, `global.SubmitEvent` and `global.PopStateEvent`

Import it before using Node.js-side modules that expect these globals.

The import keeps `window`, `location` and `history` unavailable during normal SSR. `NodeRuntime.runBrowser(...)` activates those navigation globals for an explicit test scope.

## `render(...nodes)`

`render` is the server render entry point for the same Valyrian application. It renders content into a server DOM container and serializes the result as HTML.

```tsx
import { render } from "valyrian.js/node";

const html = render(<main><h1>Hello SSR</h1></main>);
```

You can pass multiple nodes; they are rendered in order.

Serialization contract: `render(...)` escapes normal text nodes and attribute values. It preserves raw text inside `<script>` and `<style>`, and it renders raw HTML from explicit escape hatches such as `trust(html)` and `v-html`. Use those raw paths only with trusted or sanitized HTML. If you place data inside an inline `<script>`, serialize it with JavaScript-safe / JSON-safe rules before rendering.

Each `render(...)` call is isolated and does not reuse DOM state from previous calls. That per-call isolation makes request-by-request SSR safe.

## DOM Transform Utilities

Exports:

* `htmlToDom`
* `domToHtml`
* `htmlToHyperscript`
* `domToHyperscript`

```ts
import { htmlToDom, domToHtml } from "valyrian.js/node";

const dom = htmlToDom("<section><p>Hello</p></section>");
const html = domToHtml(dom);
```

## Request-Scoped DOM

`NodeRuntime.run(...)` creates an isolated document, renderer state and storage scope. The document contains one connected `html` element with `head` and `body` children.

```tsx
import { NodeRuntime, document } from "valyrian.js/node";
import { mount } from "valyrian.js";

const html = NodeRuntime.run(() => {
  mount("body", () => <main id="result">Ready</main>);
  return document.getElementById("result")?.textContent;
});
```

The Node.js surface exports the `Node`, `Element`, `Document` and `DocumentFragment` types. `Document.getElementById()` searches the connected document. `Document`, `DocumentFragment` and `Element` expose `querySelector()` and `querySelectorAll()` for this deliberately limited grammar:

* A tag, ID or class selector, such as `form`, `#login-title` or `.login-submit`.
* Attribute presence and quoted equality, such as `[data-floating]` or `[name="email"]`.
* A tag plus one attribute selector, such as `input[name="email"]`.
* Descendant combinations of those selectors, such as `form button[type="submit"]`.

Unsupported CSS syntax throws `SyntaxError`. This adapter does not claim full CSS selector compatibility. `getAttribute()` returns `string | null`, and `hasAttribute()` checks attribute presence.

`Element.click()` dispatches a bubbling, cancelable primary `MouseEvent`. Disabled buttons and inputs suppress that synthetic click. Form elements are created as `HTMLFormElement` instances, and `requestSubmit()` dispatches a bubbling, cancelable `SubmitEvent` with its `submitter`. The adapter leaves native form validation to the application.

## Test Browser Behavior Inside Node.js or Bun

Use `NodeRuntime.runBrowser(...)` to test browser-facing application behavior while the application runs completely inside Node.js or Bun. It does not open or control a real browser, and it does not require jsdom.

Inside the callback, Valyrian provides simulated browser APIs that include `window`, `document`, `location` and `history`. Combine them with `mount(...)` and the DOM adapter's event methods to test rendering, interaction and navigation in one runtime-local scope:

```ts
import { NodeRuntime } from "valyrian.js/node";

NodeRuntime.runBrowser({ url: "https://example.test/start" }, () => {
  history.pushState({ page: 2 }, "", "/next?tab=profile#details");
  console.log(location.pathname);
  history.back();
});
```

Each execution receives an isolated document, renderer state, storage, location, history stack and window event target. History traversal dispatches `PopStateEvent`. `NodeRuntime.resetHistory()` restores the scope's initial URL, one entry and a null state without removing listeners or dispatching `popstate`. It throws outside `runBrowser(...)`.

This scope supports runtime-level application tests without an external browser dependency. It does not execute the application in a real browser engine and does not replace end-to-end browser tests when you need to verify native browser behavior, layout or full user flows.

## Request-Scoped Storage

`ServerStorage` is part of the Node.js API surface for per-request storage isolation.

Use `NodeRuntime.run(() => { ... })` per incoming request. It is the recommended boundary for new SSR and server-runtime integrations because the same scope isolates the document, renderer state and storage.

`ServerStorage.run(...)` is deprecated. It remains functional throughout v9 for compatibility, but it only delegates to `NodeRuntime.run(...)` and does not create a separate storage boundary. The API may be removed in v10 under the versioning policy. That possibility is not a promise or scheduled removal date.

### Migrate from `ServerStorage.run()`

Change the import and the boundary call. The callback stays the same:

```ts
// Before
import { ServerStorage } from "valyrian.js/node";

ServerStorage.run(() => {
  // request-scoped work
});

// After
import { NodeRuntime } from "valyrian.js/node";

NodeRuntime.run(() => {
  // the same request-scoped work
});
```

See [./7.2-isomorphic-networking-and-storage.md](./7.2-isomorphic-networking-and-storage.md) for practical request-scoped usage.
